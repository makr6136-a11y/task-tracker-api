## Ungrounded Plan (repo files NOT read)

### 1. Data Model

- Define a comment entity with:
  - `id`: required UUID string, generated by the server.
  - `task_id`: required string referencing the parent task.
  - `author`: required string, 1–100 characters.
  - `body`: required string, 1–2000 characters.
  - `created_at`: required UTC datetime, generated by the server.
- Define separate input and response shapes:
  - Creation input accepts `author` and `body`.
  - The task ID comes from the route, rather than requiring the client to repeat it.
  - The response includes all comment fields.
  - Server-controlled fields must not be accepted from the client.
- Decide how comments relate to tasks and what should happen to comments when a task is deleted.

### 2. API Routes

- Add a route to create a comment for an existing task:
  - Accept the task ID in the route.
  - Validate `author` and `body`.
  - Return a not-found response if the task does not exist.
  - Generate the comment ID and UTC creation time on the server.
  - Return the created comment with the API's normal creation status.
- Add a route to list comments for a task:
  - Return a not-found response if the task does not exist.
  - Return an empty collection if the task exists but has no comments.
  - Define a stable ordering, such as oldest comment first.
- Consider whether the initial feature also requires retrieving or deleting an individual comment. Do not add those routes until their behavior and authorization expectations are decided.

### 3. Tests

- Test successful comment creation, including the generated UUID, route-derived task reference, author, body, and UTC timestamp.
- Test comments from different tasks remain correctly associated with their parent tasks.
- Test listing multiple comments in the defined order.
- Test listing an existing task with no comments.
- Test creation and listing for a nonexistent task.
- Test validation boundaries:
  - Author lengths of 1 and 100 succeed.
  - An empty author and an author longer than 100 fail.
  - Body lengths of 1 and 2000 succeed.
  - An empty body and a body longer than 2000 fail.
  - Missing `author` or `body` fails.
- Test that clients cannot control `id`, `task_id`, or `created_at`.
- Test the selected behavior when a task with comments is deleted.
- Run existing task tests to detect regressions.

### 4. Frontend Changes

- Add a comments area to the task-detail experience.
- Display each comment's author, body, and creation time.
- Add a form containing author and body fields.
- Apply client-side length constraints while retaining server-side validation as authoritative.
- Show submission, validation, loading, empty, and failure states.
- Refresh or update the displayed list after successful creation.
- Prevent accidental duplicate submissions while a request is pending.
- Confirm that comment bodies are rendered as text so user input is not treated as executable markup.
- Use an explicit display-timezone policy while preserving the server's UTC value.

### 5. Migration or data-shape notes

- If storage uses a schema, add a comments structure with a relationship or reference to tasks and an index suitable for listing by task.
- If storage is schema-free or in memory, introduce a consistent comment shape and task-to-comment lookup strategy.
- Decide whether existing stored task records need conversion. They may require no change if comments are stored separately.
- Define deletion behavior:
  - Delete associated comments with the task.
  - Preserve comments under a retained task reference.
  - Reject deletion while comments exist.
- Ensure serialized datetimes use a consistent UTC representation.
- Consider how existing development or test data will be reset or migrated.
- Document rollback or compatibility needs if older application versions may encounter the new data shape.

### 6. Open Questions

- Should the initial feature support only creating and listing comments, or also retrieving and deleting individual comments?
- What should happen to comments when their task is deleted?
- Should whitespace-only author names or bodies be rejected, and should surrounding whitespace be preserved or trimmed?
- Should duplicate comments be accepted?
- Should listing be oldest-first or newest-first?
- Is pagination needed, and if so, what are its limits and ordering rules?
- Is `author` free text, or should it eventually reference an authenticated user?
- Who may view, create, or delete comments?
- Are comments editable?
- How should creation times be displayed in the frontend?
- Are comment bodies plain text, or is any formatting supported?
- Are there retention, moderation, or audit requirements?

### Assumptions this plan makes

- Assumption: Tasks already have stable string identifiers.
- Assumption: A comment cannot exist without a corresponding task.
- Assumption: The server can generate UUIDs and timezone-aware UTC datetimes.
- Assumption: `author` is currently plain text rather than an authenticated-user reference.
- Assumption: Comment bodies are plain text.
- Assumption: The first useful API scope includes creating and listing comments; other operations require a decision.
- Assumption: Both frontend and API changes are in scope.
- Assumption: The application has some persistence or storage layer, but this plan makes no assumption about its implementation.
- Assumption: The project has an existing validation and error-response convention that the feature should follow.
- Assumption: Exact file names, route naming, storage technology, frontend framework, and test style must be determined from the repository rather than from this generic plan.

## Repo-Grounded Plan (repo files read first)

### 1. Data Model

Add the comment request and response models to `app/models.py`, alongside the existing `TaskCreate`, `TaskUpdate`, and `TaskResponse` models.

Follow the repository's current Pydantic v2 conventions:
- Use a separate creation model and response model.
- Use `ConfigDict(extra="forbid")` so unknown request fields produce HTTP 422.
- Keep server-controlled fields out of the creation model.

Proposed model responsibilities:
- `CommentCreate`
  - `author`: required string, 1–100 characters.
  - `body`: required string, 1–2000 characters.
  - Must not accept `id`, `task_id`, or `created_at`.
- `CommentResponse`
  - `id`: UUID represented as a string, matching the existing task-ID convention.
  - `task_id`: string identifying the parent task.
  - `author`: validated string.
  - `body`: validated string.
  - `created_at`: UTC-aware `datetime`.

The existing task models should remain unchanged unless the team decides to embed comments in `TaskResponse`. Keeping comments separate fits the current API better because task responses currently contain only task fields, and comments would have their own nested routes.

The exact treatment of leading/trailing whitespace is not specified. `TaskCreate.title` currently strips whitespace and rejects blank titles, but that behavior should not automatically be applied to comment authors or bodies without a team decision.

### 2. API Routes

Add the routes to `app/main.py`, where all current FastAPI routes are defined.

**Create a comment**
- Method: `POST`
- Path: `/tasks/{task_id}/comments`
- Request body: `CommentCreate` (`author`, `body`)
- Success response: HTTP 201 with `CommentResponse` (`id`, `task_id`, `author`, `body`, `created_at`)
- Behavior:
  - Confirm that the parent task exists using the storage layer.
  - Generate `id` with the same stringified UUID approach used by `app/storage.py`.
  - Generate `created_at` with a timezone-aware UTC datetime, matching task timestamp behavior.
  - Derive `task_id` from the path rather than accepting it from the request body.
- Errors:
  - HTTP 404 when the task does not exist. Follow the existing task error-detail convention in `app/main.py`.
  - HTTP 422 when `author` or `body` is missing, has the wrong type, violates its length limit, or the body contains an unknown field.

**List comments for a task**
- Method: `GET`
- Path: `/tasks/{task_id}/comments`
- Request body: None
- Success response: HTTP 200 with `list[CommentResponse]`
- Behavior:
  - Return an empty list when the task exists but has no comments.
  - Return comments in storage insertion order, matching how `get_all_tasks()` currently exposes task ordering.
- Errors:
  - HTTP 404 when the parent task does not exist.

Individual comment retrieval, editing, and deletion are not included in this initial route design because the requested feature does not define those operations.

Storage operations would belong in `app/storage.py`, following the existing separation in which `app/main.py` handles HTTP behavior and storage functions create and retrieve model objects.

### 3. Tests

Add API tests to a new `tests/test_comments.py`. This keeps comment behavior separate from the existing task tests in `tests/test_tasks.py` while retaining the current pytest style: use the shared `client` and `created_task` fixtures, issue requests through `TestClient`, and assert directly on status codes and JSON bodies.

The autouse reset fixture in `tests/conftest.py` must also clear comment storage so every test remains isolated.

- `test_create_comment_uses_task_id_from_path`
- `test_create_comment_generates_uuid_string`
- `test_create_comment_generates_utc_created_at`
- `test_list_comments_existing_task_returns_200`
- `test_list_comments_returns_comments_for_requested_task_only`
- `test_list_comments_returns_comments_in_creation_order`
- `test_list_comments_existing_task_with_no_comments_returns_empty_list`

**Validation**
- `test_create_comment_missing_author_returns_422`
- `test_create_comment_blank_author_behavior`
- `test_create_comment_author_one_character_returns_201`
- `test_create_comment_author_100_characters_returns_201`
- `test_create_comment_author_over_100_characters_returns_422`
- `test_create_comment_missing_body_returns_422`
- `test_create_comment_blank_body_behavior`
- `test_create_comment_body_one_character_returns_201`
- `test_create_comment_body_2000_characters_returns_201`
- `test_create_comment_body_over_2000_characters_returns_422`

**Edge cases**

- `test_list_comments_missing_task_returns_404_with_detail`

The final deletion test depends on the cascade-or-retain decision described below.

Existing tests in `tests/test_tasks.py` and `tests/test_health.py` should remain part of regression verification. No tests were run while producing this read-only plan.

**Gap identified in critique:** no wrong-type tests for `author`/`body` (e.g., sending a number instead of a string) were included, despite the API section stating wrong types should return 422.

### 4. Frontend Changes

The only frontend file is `frontend/index.html`. It contains the HTML, CSS, and vanilla JavaScript together and has no frontend framework or build process.

That file would need changes in four areas:

1. **Task-card controls** — Add a comments control to the markup generated by `createCardMarkup(task)`. It should open the comments interface for the selected card's `data-task-id`.
2. **Comments interface** — Add a comments panel or modal containing: the selected task's title, a list of existing comments, an empty state, an author input, a body input, a submit button, and loading/validation/failure/success behavior. The repository currently has a task create/edit modal but no separate task-detail page. Whether comments should extend that modal or use a dedicated comments modal is an open design decision.
3. **API calls** — Add frontend requests for `GET /tasks/{task_id}/comments` (on open) and `POST /tasks/{task_id}/comments` (on submit), using the existing `BASE_URL`, `fetch`, `encodeURIComponent`, and response-status checking patterns already present in `frontend/index.html`.
4. **Safe rendering and validation** — Render `author`/`body` through the existing `escapeHtml()` helper before inserting into generated HTML. Add matching client-side length limits for usability, while treating server-side Pydantic validation as authoritative.

After successful creation, update or reload the visible comment list without reloading the whole page. The interface should prevent repeated submission while the request is pending.

### 5. Migration Notes

There is no database or durable persistence. `app/storage.py` stores tasks in the process-local `_tasks` dictionary, so this feature requires no database migration or migration command.

A comments collection must be added to the in-memory storage layer. A separate module-level collection in `app/storage.py` would fit the existing design better than modifying every `TaskResponse` object. Each stored comment would carry its `task_id`, allowing the storage layer to select comments belonging to one task.

Consequences of the current storage approach:
- Comments will be lost whenever the API process restarts, just like tasks.
- Existing task objects need no data-shape conversion if comments remain separate.
- `storage._reset()` must clear both tasks and comments; otherwise comments could leak between pytest cases.
- The behavior of comments when `delete_task()` removes their parent must be defined. Leaving them behind would create orphaned task references.
- Multiple processes would not share comment data, just as they do not share task data now.

If the project later moves to a database, `task_id` would become a real foreign key or equivalent relationship. That future database design is not visible in this repository.

### 6. Open Questions

1. Should deleting a task also delete all its comments, or should task deletion be rejected while comments exist?
2. Should leading and trailing whitespace be removed from `author` and `body`?
3. Should whitespace-only authors and bodies be rejected, or do the stated length limits permit them?
4. Should comments be displayed oldest-first, matching insertion order, or newest-first?
5. Should comments appear inside the existing task create/edit modal or in a separate comments modal?
6. Should duplicate comments with the same author and body be allowed?
7. Is creating and listing sufficient for the first version, or must users also edit or delete comments?
8. Because the repository has no authentication, is a free-text `author` acceptable, even though any caller can submit any author name?
9. When comment deletion is eventually added, should deleting a comment require its task ID in the route?
10. Should task responses include a comment count, or should the frontend request comments only after the user opens the comments interface?
