# Reflection - Mid-Course Project

I used two AI tools for this project, split by task. GitHub Copilot (in VS Code) generated the actual backend and frontend code for both features - the due-date/overdue-filter model changes, the search filter, the pytest test suites, and the frontend modal/board updates. I used Claude (this chat) for planning: deciding which prompts to write, reviewing generated code before applying it, diagnosing failures, and drafting documentation. Splitting the work this way meant every piece of AI-generated code got a second, independent review pass before I trusted it, rather than one tool both writing and approving its own output.

One moment AI genuinely helped: generating the pytest suite for both features. Writing 16 tests by hand covering valid/invalid due dates, all four overdue-filter combinations, and six search scenarios (title match, description match, empty search, no match, combined with status, combined with priority) would have taken far longer manually, and the generated tests correctly matched the exact behavior I had already verified by hand with curl.

One moment AI slowed me down: reusing an old Module 1/2 prompt meant for scaffolding a brand-new project, when what I actually needed was a small, targeted addition to an already-working file. I caught this before running it by comparing the prompt's framing ("generate two files from scratch") against the task ("add one field to existing models"), but if I had run it as-is, it likely would have regenerated files I had already built on top of, costing real rework to untangle. The lesson was not that AI was wrong - it is that the same tool applied at the wrong scope creates work instead of saving it.

One place my review changed the result: Copilot claimed, confidently and in the same response, that storage.py needed "no changes" to support the new due_date field, reasoning that add_task already passed payload fields through generically. I accepted the model changes but tested the claim anyway with a real curl request - and the created task came back with due_date: null, even though I had sent a real date. Reading add_task directly showed it builds the response object from an explicit, hand-written field list that had simply never been updated to include due_date. The fix was one line, but finding it required not trusting a plausible-sounding claim about code I had not actually re-read myself.

Across both features, the pattern that mattered most was not the AI's code quality - it was consistently verifying real behavior (curl responses, actual test runs, actual file contents) instead of trusting a description of what the code should do.
